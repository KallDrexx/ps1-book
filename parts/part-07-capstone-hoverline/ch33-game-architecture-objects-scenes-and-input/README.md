# Chapter 33: Game Architecture: Objects, Scenes, and Input Events

## 1. Concept

A game is a **loop over a world of objects**. Every frame it reads the pad, updates what is in the world, and draws it. The world is a **linked list** of `Object` nodes built from a **scene file** on the disc, and a cheap **distance cull** decides which nodes are worth drawing. This chapter starts *Hoverline*, the book's capstone racer, with exactly that skeleton: a title screen, then a scene of landscape objects you can fly through.

## 2. Why it matters

Until now every program had a hard-coded handful of things. A racer has hundreds of pylons, arches, towers, later ships and pickups, and they must come from data, not from source code. A list of objects, a scene file that fills it, a state machine for menu versus game, and a cull that skips what the player cannot see are in every game of the era. They are also where 32-bit overflow stops being theory: distances across the track exceed the GTE's 16-bit range, and the squared distance of a far object does not fit in 32 bits.

## 3. Learning objectives

After this chapter you can:

- draw the main loop (input, update, render) and say what each stage may touch;
- build a singly linked list with `obj_insert` (head), `obj_append` (tail), `obj_remove` (by pointer) and walk it; name the two classic bugs, removing while iterating and dangling pointers;
- parse and validate `SCENE.BIN` (Appendix E.9), map *object -> shape index -> `.SHP` file* and load each shape once;
- cull objects by squared distance in 32-bit arithmetic without overflow, and say why checking each axis first makes it safe;
- turn a world position into a camera-relative translation the 16-bit GTE can take, and compose the object's matrix with the camera;
- use edge-triggered pad events (`pressed`, not `held`) to drive a two-state machine.

### 5.2 The game loop

```
        +-----------------------------------------------+
        |                                               |
        v                                               |
   +---------+     +----------+     +----------+        |
   |  INPUT  | --> |  UPDATE  | --> |  RENDER  | -------+     one pass = one frame
   +---------+     +----------+     +----------+
   read the pad    change the       cull, transform,
   (once)          world            link primitives, swap
```

**Input** reads the pad once and does nothing else. **Update** changes state (camera, objects, the game state) and never draws. **Render** only reads the world and fills the ordering table. Keeping the stages apart means update logic can be tested without a picture, and a skipped or repeated render cannot change the game.

Why a *world of objects*? One loop body that handles everything the same way (walk the list, ask each node what it is, act) lets you add a pylon by adding a line of data, not code. Each `Object` carries only what differs between things: which shape, where, how turned.

### 5.3 A singly linked list

An `Object` holds a pointer to the next one. The list itself is just a pointer to the first node, `head`:

```
 object_head                                                  (nodes live in object_pool[])
     |
     v
  +--------+     +--------+     +--------+     +--------+
  | next --+---> | next --+---> | next --+---> | next=0 |
  | shape  |     | shape  |     | shape  |     | shape  |
  | x y z  |     | x y z  |     | x y z  |     | x y z  |
  | ry ... |     | ry ... |     | ry ... |     | ry ... |
  +--------+     +--------+     +--------+     +--------+
     node 0         node 1         node 2         node 3        NULL ends the list
```

| Operation | Does | Cost |
|---|---|---|
| insert at head | `o->next = head; head = o` | O(1) |
| append at tail | walk to the last `next`, link `o`, `o->next = NULL` | O(n) |
| remove by pointer | find the link that points at `o`, make it point at `o->next` | O(n) |
| iterate | `for (o = head; o; o = o->next)` | O(n) |

Order matters: scene loading must **append**, so node *i* is file entry *i* (insert would reverse the file). Pick head or tail by what you need; the list does not sort itself.

**Who owns a node?** The caller. This list never allocates: `scene_load` takes nodes from a fixed `object_pool[]`; a test can hand the same functions nodes anywhere in RAM. A list with no `malloc` cannot leak and cannot run out of memory mid-frame.

**Pitfalls.**

| Bug | Why | Fix |
|---|---|---|
| removing while iterating | `obj_remove(o)` clears `o->next`; the loop's `o = o->next` then ends the walk (or follows a stale pointer) | read `next = o->next` **before** removing |
| a dangling pointer | something else still points at a removed (or reused) node | after removing, drop every other reference; here `o->next` is cleared and `visible` is per-node |
| a node in two lists, or twice | the links form a cycle; every walk loops forever | one list per node; `remove` before `insert` elsewhere |
| forgetting the head | removing the first node must change `head` itself | pass `Object **head` (a pointer to the head pointer) |

The pointer-to-pointer trick: keep `link`, the *address of the pointer that points at the node you are looking at* (first `&head`, then `&node->next`). Insertion and removal then need no special case for the first node.

### 5.4 `SCENE.BIN`: from file to list

A scene file lists *what* exists and *where*, never the models themselves (Appendix E.9). Objects point into a shape table; the table names the `.SHP` files:

```
 SCENE.BIN                                     disc
 +----------------------+
 | header 0x20          |  "SCN1", counts, offsets, cull_radius
 +----------------------+
 | shape table 16 B ea  |  0: "PYLON.SHP"  r=401  ------------> \DATA\PYLON.SHP;1
 |                      |  1: "ARCH.SHP"   r=962  ------------> \DATA\ARCH.SHP;1
 |                      |  2: "TOWER.SHP"  r=1500 ------------> \DATA\TOWER.SHP;1
 +----------------------+                  ^
 | object table 24 B ea |  shape, flags, x y z, rx ry rz, scale
 |  [0] shape 1 ...     |-----------------+   (index into the shape table)
 |  [1] shape 0 ...     |
 +----------------------+
```

Each distinct shape is loaded **once** and shared by every object that names it (the generated scene has 3 shapes for 35 objects). All three share `PROPS.TPK`, loaded once by `main.c` into the texture store of Chapter 31 (the scene file does not name it; each `.SHP` names *texture indices*). The `radius` is the shape's bounding radius about its origin; an object's own radius is `radius * scale >> 12`. `ry` is the yaw of the model's +Z axis (Chapter 25's `RotMatrix`, no sign change); `ALWAYS_DRAW` (flag bit 0) means "skip the distance rule".

Everything in the file is an input, so `scene_load` validates before it touches anything, like Chapter 32's parser. It also enforces the program's **limits**, which are what keep the arithmetic of 5.6 inside 32 bits:

| Code | Name | Condition (in this order; first failure wins) |
|---|---|---|
| -2 | `ALIGN` | image not 4-aligned |
| -3 | `MAGIC` | fewer than 4 bytes or not `SCN1` |
| -4 | `HEADER` | `size < 0x20`; `file_size != size`; `shape_count` 0 or over 16; `object_count` 0 or over 128; `shapes_offset != 0x20`; `objects_offset != 0x20 + 16*shape_count`; `size != objects_offset + 24*object_count`; `cull_radius` 0 or over 20000 |
| -5 | `SHAPE` | per shape: name empty, no NUL in its 12 bytes, or a character outside `A-Z 0-9 _ .`; radius 0 or over 6000 |
| -6 | `OBJECT` | per object (shape, flags, scale, position in order): `shape >= shape_count`; a flag bit other than bit 0; `scale` 0 or over 8192 (2.0); a coordinate beyond +-1,000,000 |
| -1 / -7 / -8 | `READ` / `SHP` / `STORE` | after validation: `cd_load_file` failed; `shp_parse` failed (`scene_shp_status` has its code); a shape needs more textures than the store holds |

A rejected file must leave the loaded scene alone; a failure after validation leaves an **empty** scene (no half-built list, no leaked file images).

### 5.5 Coordinates: the world is bigger than the GTE

Positions are `s32` world units, +Y down. The file allows +-1,000,000 per axis, and even the generated track spans about 47,000 by 26,000 units, so two points of the world can be farther apart than the 16-bit range (+-32767) of the GTE's vertex and `IR` registers. `CompMatrixLV` sends the second matrix's translation through those 16-bit registers and returns a translation saturated to 16 bits; only `TR`, where the first matrix's translation goes, is 32-bit. The cure is the one Chapter 34 uses for every track vertex: **subtract the camera first, in 32-bit C, then give the GTE only small numbers**.

```
  object position P (s32)   eye E (s32)
        \                    /
         d = P - E             s32 subtraction, any size
              |
              v      |d| <= 32000 on every axis?  no -> not drawn
   translation of the object's matrix = view rotation x d
   (vertices of the model itself are small: |v| < 1500)
```

So `draw_object` does **not** compose the object's world position with the full `view_mtx` (whose `t` is `-R * eye`): the position would pass through the 16-bit registers and be wrong as soon as a coordinate leaves +-32767. It composes with the view's *rotation* only and uses the small `d` as the translation.

### 5.6 Culling by squared distance

An object is worth drawing if the camera is within `cull_radius + object radius` of its origin (the object's far edge can still reach into range). Distance needs a square root; compare **squared** distances instead:

```
  visible  <=>  dx^2 + dy^2 + dz^2  <=  (cull_radius + radius)^2
```

Now the arithmetic. The file allows +-1,000,000 per axis, so `|dx|` can pass 1,000,000 and its square 1e12: that does not fit in 32 bits, and the *wrapped* result is a different number:

| `dx` | `dx * dx` (exact) | in 32 bits | what a naive test says |
|---|---|---|---|
| 20,401 | 416,200,801 | the same | correct |
| 46,341 | 2,147,488,281 | negative (as `int32`) | "closer than anything": drawn |
| 65,536 | 4,294,967,296 | **0** | "distance zero": drawn |

Three ways out: use 64-bit arithmetic (exact; `mult` gives a 64-bit product, but every add and compare becomes a two-word sequence), shift the values down before squaring (loses the exact boundary), or **reject by axis first**. The book's rule (`cull.h`) is the third, exact and cheap:

1. `d = pos - eye` in `s32`; if any component of `d` exceeds **`DRAW_LIMIT` = 32000** in magnitude: not drawn, whatever the flags. An object that far on one axis is beyond the cull range anyway, and the GTE could not take it. So `ALWAYS_DRAW` means "not distance-culled", not "drawn from anywhere".
2. `ALWAYS_DRAW` set: drawn.
3. Else sum the squares in **`uint32_t`** and compare with `(cull_radius + radius)^2`, **inclusive** (`<=`).

After step 1 each square is at most 1.024e9, three of them 3.07e9, below 2^32; and `cull_radius + radius` is at most 20000 + 12000 = 32000 by the limits of 5.4 (a shape radius of 6000 at scale 2.0), so its square also fits. The verifier applies the same rule with Python's exact integers.

A distance-culled object that is drawn is within 32000 of the eye, so its rotated translation also fits in 16 bits. An `ALWAYS_DRAW` object on a diagonal can be up to 55,000 away (32000 on each axis); `CompMatrixLV` then saturates its translation and the object is drawn in the wrong place. The generated scene has one such object, the start arch, and you rarely see it from that far; stretch goal 7.6 asks how to do better.

### 5.7 Drawing one object

For each visible node:

1. build its matrix: `RotMatrix` of `rx, ry, rz`, `ScaleMatrix` if `scale != 4096`, and the translation `d` of 5.5;
2. compose it with the view's rotation (`CompMatrixLV`, which also rotates the translation);
3. load the result (Chapter 25's `load_matrix` wrapper, given) and call the **given** `render_shp()`.

`render_shp` is Chapter 32's drawing: it transforms the shape's vertices, skips any polygon with a vertex nearer than 128 (the near plane), takes each packet from the primitive buffer with `ot_alloc` and links it into the ordering table.

**Budget.** The frame's primitive buffer is 2,048 bytes. A busy view can ask for more; `ot_alloc` then returns `NULL`, and `render_shp` counts that polygon and every later one of the frame in `prims_dropped` instead of writing past the buffer (the guard bytes behind it must stay `0xA5`). Which objects are dropped depends on list order: sorting nearest-first would fix that (stretch goal 7.6).

### 5.8 States and edge-triggered input

A **state machine** is a variable that says which of a few modes the program is in, and one place that decides when it changes.

```
                 Start pressed
   +---------+  ---------------->  +---------+
   |  TITLE  |                      |  GAME   |   GAME: fly camera, cull, draw the scene
   +---------+  <----------------   +---------+   TITLE: logo and a blinking bar only
                 Start pressed
```

A button has two readings (Chapter 22): **held** is true on every frame it is down, **pressed** only on the frame it went down. Menus need *pressed*. Both states test Start, so with *held* one press would enter the game, leave it on the next frame, and keep flipping the state every frame until you let go. Each state has its own update and draw code; `game_update` and `game_draw` pick by `game_state`.

## 7. Project: "Hoverline Skeleton"

### 7.1 Behavior

The program boots from the disc and shows the **title screen**: a purple gradient, the logo, a blinking yellow bar. **Start** goes to the **game**: the 35 landscape objects from `SCENE.BIN`, seen from just behind the start arch, in a dark blue sky. The Chapter 28 fly camera moves you; objects beyond the cull range disappear. **Start** again returns to the title.

Controls (the fly camera is given): D-pad moves in *world* axes (UP/DOWN = +z/-z, RIGHT/LEFT = +x/-x), R1/L1 down/up (+y is down), `cam_speed` = 200 units per frame. One addition to Chapter 28's camera, which always looked at the bouncing cube: here it looks along a heading, `cam_yaw` (0 = +z, 1024 = +x), and R2/L2 turn it by `cam_turn` = 24 per frame; the look-at itself is unchanged. Later chapters keep this camera.

### 7.2 The contract

`starter/` builds and boots (the title works), but the list, the cull, the scene loader and the game logic are stubs. **Given:** `CMakeLists.txt`, `iso.xml`, `psxe/`, `cdrom.c`, `tim.c`, `tpk.c`, `shp.c` (Chapters 29 to 32), `camera.c` (Chapter 28), `render.c` (Chapter 32's drawing), `title.c`, `main.c`, and every header: **read `object.h`, `cull.h`, `scene.h` and `game.h` first, they are the contract.** **You write:**

| File | Functions |
|---|---|
| `object.c` | `obj_insert`, `obj_append`, `obj_remove`, `obj_count` |
| `cull.c` | `cull_test(o, eye, cull_radius, &d)` |
| `scene.c` | `scene_load`, `scene_unload` |
| `game.c` | `game_update` (the state machine), `draw_scene`, `draw_object` |

**`Object`** (`object.h`, 48 bytes, twelve words, the verifier walks it): `next` +0, `shape` +4, `flags` +8, `x y z` +12, `rx ry rz` +24, `scale` +36, `radius` +40, `visible` +44.

**Rules of the scene.** The list is in the file's order (node *i* = object *i*), nodes come from `object_pool`, `radius` = table radius * scale >> 12, `visible = 0` after loading. `draw_scene` sets `visible` for every node every GAME frame, and `submitted_objects` is how many were drawn (0 in the title). Camera start: eye `(23883, -1500, -2500)`, yaw 66, `proj_h = 320`, offset `(160, 120)`.

**State the verifier reads** (names and types are fixed; `main()` keeps them linked):

| Symbol | Meaning |
|---|---|
| `game_state`, `state_changes` | `STATE_TITLE` 0 / `STATE_GAME` 1; how many times it changed since boot |
| `object_head`, `object_count`, `object_pool[128]` | the list, its length, the node storage |
| `scene_shapes[16]`, `scene_shape_count`, `scene_cull_radius` | the shape table (name, radius, loaded model), the file's cull radius |
| `scene_status`, `scene_shp_status`, `load_status`, `tpk_status` | results of loading (`load_status` 0 = fine; 100 CD, 1 pack, 2 scene, 3 logo) |
| `submitted_objects`, `prims_submitted`, `prims_dropped` | objects drawn, packets linked, polygons dropped for lack of buffer |
| `cam_eye`, `cam_yaw`, `cam_target`, `cam_up`, `cam_speed`, `cam_turn`, `cam_min`, `cam_max`, `view_mtx` | the camera: **patchable** |
| `store`, `proj_h`, `frame_no`, `frame_done()` | the texture store, projection, frames completed, the probe's marker |

### 7.3 Steps

1. `make` in `starter/`, boot it (`make run`): the title appears and Start does nothing. Run `scenedump.py`.
2. `object.c`. Compile, then reason through the cases: empty list, one node, head, middle, tail, absent node, `NULL`.
3. `cull.c`: the three steps of 5.6, in order, filling `*d` always.
4. `scene.c`: `scene_load` in the order `scene.h` gives; `validate` first, then `scene_unload`, shapes, nodes. Read fields byte by byte (the helpers are given). Check `load_status` becomes 0.
5. `game_update`: Start pressed, both ways; `camera_update()` in the game.
6. `draw_object`, `draw_scene`. First draw only the nearest object to see it; then the loop with the cull. Fly toward the arch, then turn away and watch the pylons vanish at the edge of range.
7. `verify.sh`.

### 7.4 Rules

- `input_pressed`, never `input_held`, for Start.
- No `malloc` for nodes; nothing that depends on this scene (counts, positions, shape indices, the cull radius, the radius of a shape): the verifier boots a second disc with another scene.
- Do not read a byte of the scene before the checks so far prove it is inside the file; never advance a pointer by a `sizeof` the file did not define.
- Do not use `view_mtx.t` for objects (5.5).

### 7.5 Hints

- `obj_remove`: a loop with a `link` of type `Object **`; compare `*link` with `o`.
- `cull_test`: write the three steps as three `if`s; use `uint32_t` for the sum.
- `scene_load`: split into `validate()` and a loader; one loop per table, in the file's order, keeps the order of the checks visible.
- Remove-while-iterating bugs show up when you call `obj_remove` in a loop: save `next` first.
- In `draw_object`, copy `view_mtx` and zero its `t` rather than editing the global.

### 7.6 Stretch goals

- Sort by distance and draw nearest first, so that a full buffer drops the far objects (5.7).
- Draw `ALWAYS_DRAW` objects correctly beyond 32000 units: what would you have to give the GTE instead (5.6)?
- Add a pause state with Select.
- A frame-time readout: what fraction of a frame (566,120 CPU cycles in PCSX-Redux, NTSC) does the cull cost for 128 objects?

## 9. Common pitfalls

- **Squaring before limiting.** `dx*dx` at `dx = 65536` is 0 in 32 bits; the object appears at distance 0.
- **Forgetting the object's radius.** An object whose origin is just outside the range still reaches inside it and pops.
- **`<` versus `<=`.** The rule is inclusive; the verifier puts a camera exactly on the boundary.
- **Removing inside the iteration** without saving `next`.
- **Inserting where you meant to append.** The list reverses the file; positions still match but node *i* is not entry *i*.
- **A removed node's stale `next`.** Clear it, or you walk into the old list.
- **Using `view_mtx.t` for objects.** The object's world position then goes through `CompMatrixLV`'s 16-bit registers, and the file allows +-1,000,000. Use the rotation and `d`.
- **Level-triggered Start** flips the state every frame while held.
- **Radius from the `.SHP` or a constant.** It comes from the scene's shape table times the object's scale.
- **Trusting the file.** A scene is data: check the sizes and indices before using them, and check `cull_radius + radius` stays in range.
